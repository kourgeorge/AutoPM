02 / THE DATA STRUCTURE

The files act like tables.

The app stores JSON documents and record collections directly on disk. The ERD shows logical relationships implemented by the code.

JSON: one current document

Settings and engine state are saved as complete documents. Nested objects hold the actual fields.

JSONL: a collection of records

Each line has a small envelope plus a value. An update can append another line with the same id; the last version wins.

The common record envelope

{
  "seq": 42,
  "id": "ord-demo",
  "at": "2026-01-05T15:00:00Z",
  "value": { "kind": "entry", "status": "pending", ... }
}
Fictional example

id identifies a record within its collection.

seq orders inserted records. Updates retain the record’s original sequence.

at is the envelope time. Updates may retain it; use payload timestamps for specific events.

value contains the entity’s own fields. It is usually an object with the entity’s own id repeated inside.

On load, superseded versions are compacted away. A record that needs its own history keeps it inside itself, as an order’s history[] does. References are checked by application code; there are no SQL foreign-key constraints.

An order has its own lifecycle.
Approval, submission and execution are separate states. The order record holds the current state, and its history[] keeps each step.

Before submission
A pending request can be approved, rejected or expired. Approved orders can expire or fail during validation.
Partial or complete
A submitted order can remain open, partially fill, or finish. A full fill may go directly to executed without a partial stage.
Unknown outcome
If the engine cannot establish the broker outcome, it marks the order unknown, pauses trading and puts a warning in the feed. Reconciliation can later resolve it.
Duplicate prevention has several layers. An order’s dedupKeys let a repeated request reuse it. Tool receipts reuse completed attempts. clientOrderId identifies the broker submission. Reconciliation checks existing outcomes before another order could be sent.
The rail shows a common entry/exit path, not every allowed transition. Stop/target adjustments can finish without creating a new buy/sell fill.


07 / THE DATA STRUCTURE
Where is the position?
The current holding is read from the broker. The app keeps local management metadata under state.positionSnapshots[symbol].
Broker: what exists now
Current quantity, average cost and open orders are broker reads. There is no positions table. orders.jsonl holds the app’s own order requests, not the broker’s open orders.
State: how we manage it
Stores the entry link, original entry price, observed high/low, intended stop/target and broker protection order ids.
Protection plan
Before sending a protective order, the manager saves an intent. Only its latest status is kept, in state. Your commands that clear or confirm it are logged in alerts.

08 / THE DATA STRUCTURE
Why did we enter, and should we stay?
An entry thesis lives inside the original journal decision. Material holding reviews refer back to that entry and to saved tool results.
Original entry thesis
The thesis contains a setup, intended holding horizon, catalyst-risk choice and premises. Each premise contains a label, metric, optional numeric condition and observation references. Those references are receipt ids in tool-calls.
Later holding review
A position review (the receipt of record_position_review, in tool-calls) records keep/reduce/exit/wait, changed evidence, unknowns and a next review date. entryDecisionId ties it to this holding’s entry lifecycle.
Illustrative nested thesis — there is no separate theses or premises table
{ "setup": "Trend continuation", "horizonDays": 20,
  "premises": [{ "label": "Momentum remains supported", "metric": "rsi",
    "operator": "gt", "threshold": 50, "evidenceIds": ["req-demo:1:0"] }] }
A review is an assessment
Saving a holding review writes no journal row; the review is the record of the hold. A reduce/exit assessment needs a separately requested order to change the account.
A candidate is not held
A candidate review (the receipt of record_candidate_review) keeps material buy/wait/skip reasons, and can carry a proposed thesis and a link to its entry plan. Its snapshot must confirm the instrument is not held. It creates no fill or entry order by itself.
Legacy entries can have thesis:null. Numeric checks can be supported, contradicted or unknown. Qualitative premises remain unknown to numerical checking.


09 / THE DATA STRUCTURE
Research has three stages.
Finding a headline, reading its original source and interpreting it fill in one sources row, then one review receipt.
1. Discover
Each news item or SEC filing gets one row in sources: a stable id (source-…), title, URL, publisher and known dates. The engine can find it without reading the full text.
2. Read
read_source fetches the readable text and saves it on the same row, with fetchedAt and the final URL. Later pages use that saved version.
3. Interpret
record_research_review saves the judgement as its own receipt in tool-calls: supports/contradicts/irrelevant/uncertain, a reason and the premise being discussed. Support or contradiction is only accepted once the text has been read.
publishedAt
When the publisher says it was published.
eventAt
When the underlying event occurred, if known.
firstSeenAt
When this engine registered the source.
fetchedAt
When the original text was retrieved.
The source row holds discovery → text. Each assessment is a separate receipt; the newest one naming the source is its current reading. affectedPremise is descriptive text; it is not a foreign key into a premise table. Missing dates stay unknown.


10 / THE DATA STRUCTURE
How the agent retrieves large information.
A model can only receive a limited amount of text at once. Complete records remain available through retrieval tools.
Full tool result → tool-calls
A long result is saved completely. The model gets its receiptId and can call get_tool_result to read exact character pages.
Cut text → trajectories
When the cycle brief is too long, or older exchanges are trimmed to fit, the full text is kept in the trajectory’s saved map. get_saved_context uses its id (<requestId>:context-<n>) to read it back.
Long list → the same receipt
A paged tool keeps its full result in the receipt’s snapshot field. The receipt id is the snapshotId; with an offset it returns stable rows, and nextOffset says whether more remain.
Measured observation → the same receipt
An evidenceId is the receipt id of the tool call that measured it. get_evidence reads it back from tool-calls. Observations from the cycle brief get their own receipt, id evidence-<uuid>.
Most ids point to one place. receiptId, evidenceId, a review’s snapshotId and a paged tool’s snapshotId all → tool-calls. Only get_saved_context’s snapshotId → trajectories (its saved map).
Saving proves the information is retrievable. It does not prove the agent fetched or used every omitted section.


11 / THE DATA STRUCTURE
Lessons and follow-up answer different questions.
Lessons store advisory observations. Follow-up calculations describe later market paths from the recorded decision reference.
Lesson: what we think we learned
Stores text, supporting decisions, counter-decisions, scope, sample counts, strategy fingerprint, review date and active status.
Follow-up: what happened afterward
Reads position and candidate reviews and observation-linked entry/exit decisions. Calculates passive 1/5/20-session stock paths and benchmark comparisons.
↳
Important naming trap
lessons.evidenceIds points to journal decisions.
A review’s evidenceIds points to saved tool results in tool-calls.
Actual trade results
The fills ledger is the input for realized trade accounting. These calculations are derived; this folder has no separate scorecard or follow-up table.
What remains unproven
Passive paths exclude later orders, stop execution and full trading costs. Their context-group averages do not establish that the new information improves trading.


12 / THE DATA STRUCTURE
Events, the feed and recovery.
These records explain what woke the engine, what the operator was told, and what happened during manual recovery.
Alerts: a detected condition
Detectors publish conditions. The event bus manages confirmation, crossings, rearming bands, cooldowns and escalation. Pending events also live in state.
Warnings: tell the operator
Approval-needed and uncertain-outcome warnings appear in the feed. If a webhook is set, a retry outbox in state delivers them too.
Activity: show the timeline
The dashboard and terminal read the activity feed. A tool line keeps its summary and receipt id; its full output is loaded from tool-calls when you expand it.
Acknowledge or act
An alert can be observed, declined, order_pending or resolved. “Acting” requires a linked valid order. Acknowledgement alone sends no order, and its note stays on the alert.
Manual recovery
Explicit commands can adopt a holding, clear an unplaced protection request or confirm existing broker protection. Each command is logged in alerts as an operator_command event.
Logical event id lives in alerts.value.id. The alert envelope id adds wakeCount, so escalations have distinct logged entries. An order’s eventId points to the logical event.

14 / THE DATA STRUCTURE
Restart: what gets preserved?
Records are written to disk as the work happens, so a restart picks up where things stopped. Nothing needs converting first.
1. Changes add lines
Each change adds one line to a collection file. Several lines can share an id; the last line for that id wins. Older lines are not edited in place.
2. Loaded into memory at start
On start the app reads each file, keeps the latest version of every record and drops the older copies. Settings and state are read back as whole documents.
3. Interrupted turns resume
A trajectory is saved after every model round. When a stopped turn resumes, a tool call that already has a saved result is not run again; the saved result is reused.
Normal storage writes
Records are staged in memory; a synchronous transaction callback that throws is rolled back. At commit, log lines append and changed documents are written. Startup compacts superseded row versions.
The practical boundary
This file-based storage has no SQL foreign-key engine or atomic commit across all files. Receipts, order histories, protection plans and reconciliation support recovery; they do not turn every filesystem write into a distributed transaction.
Outside the app tables: .DS_Store is Finder metadata. A backup is simply a copy of the db/ folder. Historical bar caches are separate market-data files. aiDecisionCache.json, fundamentals.json and sectors.json beside db/ are caches too.


15 / THE DATA STRUCTURE
Which records answer which question?
Use this as a practical guide when inspecting a trading decision or investigating an unexpected outcome.
Why did it enter or exit?
Start with the journal rationale and thesis, then follow its order and observation links.
Did anything actually trade?
Check broker executions in fills and the order’s confirmed outcome. A queued intent alone is insufficient.
Why did it hold or skip?
Inspect the position or candidate review receipts, the note on the alert it answered, and skip rows in the journal.
What did the agent see?
Read the trajectory and tool receipts. Text cut from the context is in the trajectory’s saved map; paged results and observations are on the receipts; news and filings are in sources.
Was the position protected?
Inspect local protection metadata and the latest protection plan, then verify current coverage against broker open orders.
Did the extra context help?
The current records support inspection and future evaluation. They do not provide a controlled demonstration of improved trading performance.

A few rules make the structure easier to read.
These distinctions apply across every table and mechanism in this presentation.
01
Intent and execution are separate.
journal explains the decision; orders tracks its lifecycle; fills records actual executions.
02
A reference is just an id with a meaning.
Read the field in context. An observation, request, order, source and broker order have different identities.
03
Current state and history have different jobs.
state is operational memory. alerts, journal and an order’s own history[] keep changes over time.
04
Stored information is not proof of better trading.
These records make decisions more inspectable. Their investment value still requires evaluation.
