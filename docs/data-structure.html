02 / THE DATA STRUCTURE

The files act like tables.

The app stores JSON documents and record collections directly on disk. The ERD shows logical relationships implemented by the code.

JSON: one current document

Settings and engine state are saved as complete documents. Nested objects hold the actual fields.

JSONL: a collection of records

Each line has a small envelope plus a value. An update can append another line with the same id; the last version wins.

The common record envelope

{
  "seq": 42,
  "id": "action-demo",
  "at": "2026-01-05T15:00:00Z",
  "value": { "kind": "entry", "status": "pending", ... }
}
Fictional example

id identifies a record within its collection.

seq orders inserted records. Updates retain the record’s original sequence.

at is the envelope time. Updates may retain it; use payload timestamps for specific events.

value contains the entity’s own fields. It can even be a string, as in action-dedup.

On load, superseded versions are compacted away. Dedicated histories such as action-history retain separate snapshots with their own ids. References are checked by application code; there are no SQL foreign-key constraints.

An action has its own lifecycle.
Approval, submission and execution are separate states. The action record holds the current state; action-history preserves each transition.

Before submission
A pending request can be approved, rejected or expired. Approved actions can expire or fail during validation.
Partial or complete
A submitted order can remain open, partially fill, or finish. A full fill may go directly to executed without a partial stage.
Unknown outcome
If the engine cannot establish the broker outcome, it marks the action unknown and pauses. Reconciliation can later resolve it.
Duplicate prevention has several layers. action-dedup reuses an equivalent local request. Tool receipts reuse completed attempts. clientOrderId identifies the broker submission. Reconciliation checks existing outcomes before another order could be sent.
The rail shows a common entry/exit path, not every allowed transition. Stop/target adjustments can finish without creating a new buy/sell fill.

Where is the position?
The current holding is read from the broker. The app keeps local management metadata under state.positionSnapshots[symbol].
Broker: what exists now
Current quantity, average cost and open orders are broker reads. There is no persistent positions.jsonl or orders.jsonl table in this folder.
State: how we manage it
Stores the entry link, original entry price, observed high/low, intended stop/target and broker protection order ids.
Protection history
Before sending a protective order, the manager saves an intent. Its later status is recorded in state and appended to the protection history.

08 / THE DATA STRUCTURE
Why did we enter, and should we stay?
An entry thesis lives inside the original journal decision. Material holding reviews refer back to that entry and to measured observations.
Original entry thesis
The thesis contains a setup, intended holding horizon, catalyst-risk choice and premises. Each premise contains a label, metric, optional numeric condition and observation references.
Later holding review
The review records keep/reduce/exit/wait, changed evidence, unknowns and a next review date. entryDecisionId ties it to this holding’s entry lifecycle.
Illustrative nested thesis — there is no separate theses or premises table
{ "setup": "Trend continuation", "horizonDays": 20,
  "premises": [{ "label": "Momentum remains supported", "metric": "rsi",
    "operator": "gt", "threshold": 50, "evidenceIds": ["evidence-demo"] }] }
A review is an assessment
Saving a holding review also creates a journal hold decision. A reduce/exit assessment needs a separately requested action to change the account.
A candidate is not held
candidate-reviews preserves material wait/skip reasons. Its snapshot must confirm the instrument is not held. It creates no fill or entry action.
Legacy entries can have thesis:null. Numeric checks can be supported, contradicted or unknown. Qualitative premises remain unknown to numerical checking.


09 / THE DATA STRUCTURE
Research has three stages.
Finding a headline, reading its original source and interpreting it are stored separately.
1. Discover
research-items gives a source a stable id, title, URL, publisher and known dates. The engine can discover it without reading the full text.
2. Read
read_source fetches readable text and caches it in source-text under the same source id. Subsequent pages use that saved version.
3. Interpret
research-reviews records supports/contradicts/irrelevant/uncertain, a reason and the premise being discussed. Strong support/contradiction requires fetched text.
publishedAt
When the publisher says it was published.
eventAt
When the underlying event occurred, if known.
firstSeenAt
When this engine registered the source.
fetchedAt
When the original text was retrieved.
The source id connects discovery → text → interpretations. affectedPremise is descriptive text; it is not a foreign key into a premise table. Missing dates stay unknown.


10 / THE DATA STRUCTURE
How the agent retrieves large information.
A model can only receive a limited amount of text at once. Complete records remain available through retrieval tools.
Full tool result → tool-calls
A long result is saved completely. The model gets its receiptId and can call get_tool_result to read exact character pages.
Omitted text → contexts
Whole cycle sections or older conversation exchanges are archived. get_saved_context uses the archive id to recover the saved text.
Long list → pages
The first paginated request saves the full result. snapshotId and offset retrieve stable rows; nextOffset signals whether more remain.
Measured observation → evidence
An evidenceId lets the agent or reviewer retrieve the specific observation used in a thesis or review, including its source and timing.
The same word can mean different references. receiptId → tool-calls. evidenceId → evidence. A position-review snapshotId → evidence. A paginated tool snapshotId → pages. get_saved_context’s snapshotId → contexts.
Archiving proves the information is retrievable. It does not prove the agent fetched or used every omitted section.


11 / THE DATA STRUCTURE
Lessons and follow-up answer different questions.
Lessons store advisory observations. Follow-up calculations describe later market paths from the recorded decision reference.
Lesson: what we think we learned
Stores text, supporting decisions, counter-decisions, scope, sample counts, strategy fingerprint, review date and active status.
Follow-up: what happened afterward
Reads position/candidate reviews and observation-linked entry/exit decisions. Calculates passive 1/5/20-session stock paths and benchmark comparisons.
↳
Important naming trap
lessons.evidenceIds points to journal decisions.
position-reviews.evidenceIds points to observation snapshots in evidence.
Actual trade results
The fills ledger is the input for realized trade accounting. These calculations are derived; this folder has no separate scorecard or follow-up table.
What remains unproven
Passive paths exclude later actions, stop execution and full trading costs. Their context-group averages do not establish that the new information improves trading.


12 / THE DATA STRUCTURE
Events, messages and recovery.
These records explain what woke the engine, what the operator was told, and what happened during manual recovery.
Alerts: a detected condition
Detectors publish conditions. The event bus manages confirmation, crossings, rearming bands, cooldowns and escalation. Pending events also live in state.
Notifications: tell the operator
Approval and uncertainty messages are recorded. Optional webhook delivery keeps a retry outbox in state and can create notifications-sent.
Activity: show the timeline
The dashboard reads an activity stream. It can include tool references, but authoritative action status and full receipts live in their own collections.
Acknowledge or act
An alert can be observed, declined, action_pending or resolved. “Acting” requires a linked valid action. Acknowledgement alone sends no order.
Manual recovery
Explicit commands can adopt a holding, clear an unplaced protection request or confirm existing broker protection. Their command-specific payloads are recorded.
Logical event id lives in alerts.value.id. The alert envelope id adds wakeCount, so escalations have distinct logged entries. An action’s eventId points to the logical event.

14 / THE DATA STRUCTURE
Migration and restart: what gets preserved?
The decision-context migration adds absent metadata to older records. It does not invent the thesis or evidence the old agent never recorded.
1. Snapshot the old database
The offline script acquires the engine lock, copies the original files into the account’s backups directory and records checksums.
2. Add missing metadata
Adds explicit null/empty legacy fields and links exact matching tool receipts where unambiguous. Existing ids, values and row versions are preserved during conversion.
3. Record completion
The audit stores the migration id, changed-record counts and backup path. Rerunning it recognizes the marker and avoids repeating the conversion.
Normal storage writes
Records are staged in memory; a synchronous transaction callback that throws is rolled back. At commit, log lines append and changed documents are written. Startup compacts superseded row versions.
The practical boundary
This file-based storage has no SQL foreign-key engine or atomic commit across all files. Dedicated receipts, histories, intents and reconciliation support recovery; they do not turn every filesystem write into a distributed transaction.
Outside the app tables: .DS_Store is Finder metadata. Backups are under data-alpaca/backups/. Historical bar caches are separate market-data files. Conditional notifications-sent.jsonl may appear when delivery is used.


15 / THE DATA STRUCTURE
Which records answer which question?
Use this as a practical guide when inspecting a trading decision or investigating an unexpected outcome.
Why did it enter or exit?
Start with the journal rationale and thesis, then follow its action and observation links.
Did anything actually trade?
Check broker executions in fills and the action’s confirmed outcome. A queued intent alone is insufficient.
Why did it hold or skip?
Inspect material position or candidate assessments, unknowns and the cited observations.
What did the agent see?
Read the transcript and tool receipts. Follow referenced archives and snapshots for omitted or paginated content.
Was the position protected?
Inspect local protection metadata and intent history, then verify current coverage against broker open orders.
Did the extra context help?
The current records support inspection and future evaluation. They do not provide a controlled demonstration of improved trading performance.

A few rules make the structure easier to read.
These distinctions apply across every table and mechanism in this presentation.
01
Intent and execution are separate.
journal explains the decision; actions tracks its lifecycle; fills records actual executions.
02
A reference is just an id with a meaning.
Read the field in context. An observation, request, action, source and broker order have different identities.
03
Current state and history have different jobs.
state is operational memory. action-history and stop-requests preserve selected changes over time.
04
Stored information is not proof of better trading.
These records make decisions more inspectable. Their investment value still requires evaluation.
