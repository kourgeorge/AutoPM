AutoTrade — System Architecture & Data Flow

How every file is written, who reads it, and what it means for building a self-improving portfolio health loop.

1 · The Architecture in One Picture

The system is organised into five numbered layers (L0–L5). Each layer knows only about the layers below it. The LLM never touches the broker directly; it always acts through tools, and tools write structured records that outlive any single cycle.

L0 policy.yaml → All behavioural numbers live here — immutable ceilings enforced at load, never in code.
L1 Broker / Market Data → L2 FeatureScheduler + Detectors → state.json + EventBus (in-memory)
L2 EventBus → L3 Trader Agent → tools → journal.jsonl + fills.jsonl + LESSONS.md
Trader → guard → L4 Risk Guard → broker → L1 Venue (Alpaca / IBKR)
ConciergeAgent reads state.json + journal.jsonl ; sends messages → Trader

2 · The Data Files — Exact Roles

data/state.json
Mutable durable state L2

The only file the scheduler's deterministic layer writes. Holds today's start-of-day equity, per-position baselines (entry price, stop, target, session high/low), and the event-bus trigger ledger (cooldowns + armed keys). Debounced 5 s on write — coalescing many writes per tick is intentional.

data/journal.jsonl
Append-only decision log L5

One JSON object per line, written synchronously (no debounce). Every decision the Trader makes — entry, exit, hold, veto by guard, rejection by venue — lands here with its rationale, intended stop/target, ATR at entry, and policy version. Torn on kill; a torn line is skipped on read, never thrown.

data/LESSONS.md
Standing rules of thumb L5

Free-text markdown, appended synchronously, never rewritten by the system. The only edge that carries an inference from one cycle into the next. The Trader reads up to 20 recent lessons at cycle start; the operator can hand-edit or delete lessons that turned out wrong.

data/fills.jsonl
Durable fills ledger L4

Broker fills copied here by the reconciler every 5 min and at every session close. Deduplicated by fill-id. IBKR discards fills overnight — this is the only record that survives. Feeds computeOutcomes() → scorecard() for the metrics the Trader reads.

Why state.json is debounced but journal.jsonl is synchronous.
state.json holds current status — coalescing 30 writes in one tick is a feature, a final write is all that matters. journal.jsonl holds what happened — a record that was sitting in a timer when the process died is worthless precisely when it was needed most. The fills ledger follows the same rule.

3 · state.json — Field-by-Field

FieldWritten byRead byPurpose
startOfDayEquity Scheduler (resetDailyState) on first tick of each ET trading day Detectors: dailyLossDetector The denominator for the daily-loss-limit check. Only updated when the account read succeeds — a stale baseline is safer than a wrong one.
lastResetDate Same as above Scheduler (ensureDailyReset) Guards against a double-reset on the same ET date. ET date, not UTC — rolling at midnight ET not UTC prevents a mid-evening re-baseline.
positionSnapshots Trader (on fill via openPositionSnapshot); L2 scheduler (patchPositionSnapshot for sessionHigh/Low) Trader cycle context; stop/drawdown detectors; Concierge get_state Durable baselines: entryPrice set once at fill and never overwritten. sessionHigh/sessionLow monotonically updated each tick. entryDecisionId links back to the journal record that holds the entry rationale.
eventCooldowns EventBus (disarm) on each event that fires EventBus gate 3 (cooldown check) on every detector hit Maps cooldownKey → ISO last-fired timestamp. Prevents a continuous breach from generating a wake storm. Cleared wholesale on daily reset so the new session is measured fresh.
armedTriggers EventBus (rearm / disarm) on every tick that sees a threshold recross EventBus gate 1 (edge gate) on every detector hit The set of keys that have recrossed their threshold band and are ready to fire again. Persisted so a restart doesn't re-announce everything the previous process already handled.
lastReviewedExitAt Scheduler (publishReviewReady) after each reconcile Same function — it's a watermark ISO timestamp of the newest exit the Trader has already been shown a review_ready event for. Prevents re-announcing the whole history on every reconcile run.

4 · journal.jsonl — Field-by-Field

Every record is a DecisionRecord. Its id is ${kind}:${symbol}:${iso} — greppable and symmetric with event IDs so a veto can be matched to the event that triggered it.

FieldValuesPurpose
kind entry | exit | hold | veto | rejected What happened. hold records deliberate decisions NOT to act — a trade list can never show these, but they are the decisions that explain a flat book.
actor trader | guard | broker Who stopped it. veto = guard refused before the venue. rejected = guard allowed it, broker said no.
triggerEventId Event id or null Links a decision back to the machine event that prompted it. Enables "how many stop-breach events were acted on vs ignored."
rationale Free text (140 chars in cycle context) The model's stated reason. Shown verbatim in the cycle context for open positions so a later cycle reads the original thesis, not a reconstruction.
intendedStop / intendedTarget Absolute price or null What was intended, recorded even on vetoes. A veto with no intended stop is indistinguishable from one with a bad stop unless these are here. Also powers expectancyR in the scorecard.
atrAtEntry Number or null The ATR the stop was sized against. Lives here (not in state) because it is the moment of entry ATR, not the current one.
vetoRule Rule name or null Which guard rule refused the intent — enables "what fraction of entries are blocked by the position-count ceiling vs the daily-loss ceiling."
policyVersion Integer Which policy was active at decision time. The scorecard's byPolicyVersion breakdown uses this to isolate whether a rule change moved performance.
Journal is a witness, not a participant.
A write failure in recordDecision is logged and swallowed. A full disk must not turn a filled order into a thrown exception the model reads as a failed one. The order goes through regardless; the record might not. This is the correct trade-off.

5 · How the Trader Agent Interacts with Both Files

5a · At cycle start — reading

Every cycle builds a fresh context object (buildCycleContext) from scratch. Nothing is remembered between cycles except what is persisted to disk. The context includes:

Context blockSource
=== PORTFOLIO CONTEXT ===state.json → positionSnapshots joined with live venue positions. Each row shows entry price, stop, target, sector weight, MFE/MAE, and the verbatim entry rationale retrieved by entryDecisionId from journal.jsonl.
=== MACHINE EVENTS ===EventBus in-memory pending queue (backed by state.json → armedTriggers and eventCooldowns for deduplication). Shows severity-sorted events with their IDs.
=== RECENT DECISIONS ===journal.jsonl — last 8 records. Shows kind, symbol, qty/price, P&L, and rationale or veto rule.
=== LESSONS ===LESSONS.md — last 20 lessons, rendered in full. The only cross-cycle inference memory.

5b · During a cycle — writing

The Trader calls tools. Every tool that acts writes records:

Trader calls execute_entry → journal.jsonl (entry record + entryDecisionId)
+ state.json → positionSnapshots gets entryPrice, stopLevel, takeProfitLevel, openedAt set ONCE and never overwritten
Trader calls execute_exit → journal.jsonl (exit record with P&L)
+ state.json → positionSnapshots entry for that symbol is removed
Trader calls ack_event → EventBus marks event acked in-memory. State updated (cooldowns). A hold/veto may also be written to journal.jsonl.
Trader calls write_lesson → LESSONS.md appended synchronously with timestamp and policy version
Trader calls sleep(minutes, reason) → Cycle ends. Next cycle will be woken in N minutes unless a critical event fires first.

6 · How the Concierge Agent Interacts with Both Files

The Concierge is the operator-facing layer only — it never places orders directly. Its interactions with the data files are all read-only, except for one relay path:

ToolWhat it reads / does
get_state Reads state.json: startOfDayEquity, lastResetDate, positionSnapshots (entry, stop, target, MFE/MAE). Also reads policy.yaml watchlist.
get_journal(symbol?, limit?) Reads journal.jsonl via readDecisions(). Returns up to 200 records, filtered by symbol if provided. The Concierge uses this to explain why a trade was or wasn't taken.
get_pending_events Reads the in-memory EventBus pending queue. Cooldown state is backed by state.json but events themselves are in-memory.
send_to_trader(message) Calls trader.wake(message). The message is queued in pendingMessages[] and appears in the Trader's next cycle context under === OPERATOR INSTRUCTIONS ===. No file write.
update_policy Mutates policy.yaml via mutatePolicy(). The Trader hot-reloads policy at the start of each cycle, so changes take effect on the next cycle with no restart required.

7 · The Event Bus and state.json Trigger Ledger

The EventBus is the most subtle interaction between state.json and the agents. It applies four gates to every detector hit before waking anyone:

  1. Edge gate — fires only on false → true transitions. Armed state persisted in state.json → armedTriggers so a restart doesn't re-fire everything.
  2. Hysteresis — re-arming requires recrossing the threshold by a configurable band (in policy.yaml → triggers.hysteresisPct). Kills boundary flutter.
  3. Cooldown — even a freshly re-armed key stays quiet inside defaultCooldownMs. Last-fired timestamps stored in state.json → eventCooldowns.
  4. Escalation — a critical event still breaching and still unacked re-fires at criticalCooldownMs with wakeCount++. This is what enforces attention: ignore a stop breach and wakes get louder.
Daily reset clears all trigger latches.
At the start of each ET trading day the scheduler empties both eventCooldowns and armedTriggers wholesale. This prevents a key that fired yesterday from being silenced forever when its threshold un-breaches overnight (measured in production: 13 of 35 keys were permanently muted before this fix). Each new day, every condition can report once, measured against that day's prices.

8 · The Learning Loop — How the System Improves

The system has a structured, multi-layer feedback loop. Each layer feeds the next:

fills.jsonl → computeOutcomes() → scorecard() → Trader reads via get_scorecard
Trader infers conclusion from scorecard → calls write_lesson → LESSONS.md → shown to the Trader on every future cycle
Operator / Concierge → update_policy → policy.yaml → hot-reloaded next cycle; version stamped on every journal record thereafter
Reconciler (every 5 min + session close) → publishReviewReady → Trader woken with review_ready event → journal.jsonl

9 · Roadmap: Making the System Semi-Automatic & Self-Improving

The architecture already has all the wiring needed. The gaps are in portfolio health assessment and closed-loop policy mutation. Below is a concrete phased roadmap.

Phase 1 — Portfolio Health Score (observable today)

1

Add a get_portfolio_health tool

Combines scorecard(), exposure(), and stop discipline into a single JSON object. Grade each dimension (P&L vs benchmark, concentration risk, stop compliance rate, win rate trend over last 30 vs 90 days). The Trader calls this at every review_ready event and writes a lesson if any dimension degrades by a threshold.

2

Emit a health_degraded event from a new detector

A new portfolioHealthDetector runs in the scheduler tick, reads the fills ledger, and fires an urgent event when rolling 14-day expectancy drops below a configurable floor. The event wakes the Trader without operator input. Gate it with a 6-hour cooldown so one bad stretch doesn't flood the queue.

3

Surface health to the Concierge as a push alert

The router already calls concierge.pushAlert(msg) for critical events. Route health_degraded through this path so the operator sees a plain-language summary without asking.

Phase 2 — Automated Policy Suggestions (semi-automatic)

4

Give the Trader a propose_policy_change tool (dry-run only)

The Trader can call this to write a proposed change to a staging file (data/policy_proposal.json) with full rationale and scorecard evidence. It never mutates policy.yaml directly. The proposal lands in the journal as a hold record with kind policy_proposal.

5

Concierge reviews proposals on operator request

Add a get_policy_proposals tool to the Concierge that reads data/policy_proposal.json and presents the rationale. The operator approves or rejects via send_to_trader("apply proposal") or send_to_trader("reject proposal: reason"). The Trader then calls update_policy or records a rejection in the journal.

6

Auto-approve low-risk proposals after a confirmation window

If a proposal has been sitting for 24 hours with no rejection and the change is within a safe band (e.g. ±10% on position size, no watchlist removals), the Trader can auto-apply it on the next morning cycle. Record it as an entry-kind journal record with actor trader and rationale citing the proposal.

Phase 3 — Watchlist Self-Management (autonomous)

7

Promote ideaCandidates and shadowWatch from state

state.json already has ideaCandidates, watchlistExtension, and shadowWatch fields (currently empty arrays). Populate them: shadowWatch = symbols that have passed signal scoring but not yet on the watchlist; ideaCandidates = symbols under research. The Trader manages these lists as part of the research cycle.

8

Auto-graduate shadow-watched symbols to the watchlist

A symbol that has scored positively on all five entry signals for N consecutive ticks, passes correlation check, and fits sector exposure budget is promoted via update_policy({ addToWatchlist: [symbol] }) automatically. The journal records the promotion with the signal evidence. No operator action needed.

9

Auto-remove consistently poor performers from the watchlist

A symbol with ≥ 5 completed round trips, negative expectancy, and no open position is proposed for removal from the watchlist. The Trader calls propose_policy_change with scorecard evidence. This closes the portfolio health loop: the system stops allocating attention to symbols that have repeatedly failed.

Phase 4 — Resilience & Observability

10

Add a data/health_log.jsonl file

A structured record written by the scheduler every day at reset time: equity, positions count, deployed %, daily P&L, open event count. Lets the Concierge answer "how has the portfolio been doing over the last 30 days?" without replaying the fills ledger. One line per day = ~1 KB/year.

11

Repair missing position snapshots automatically

On startup repairSessionExtremes already restores MFE/MAE. Extend it to detect holdings at the venue with no snapshot at all (currently flagged "NO STOP RECORDED HERE") and attempt to reconstruct them from the fills ledger. Write a warning lesson if reconstruction is needed — the system should not silently hold an unmonitored position.

The architecture supports all of this today.
Every step above uses only mechanisms that already exist: journal records, state patches, tool calls, event publication, and policy hot-reload. No structural changes are required — only new detectors, new tools, and new decision paths for the Trader and Concierge to walk.
